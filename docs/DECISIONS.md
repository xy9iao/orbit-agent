# Decisions

Each entry says what we chose, why, and what happens when it fails. The first section restates the foundational choices from PLAN.md's Decisions table with their failure modes; the rest were made during the build, in milestone order of when they came up.

## Foundational choices (PLAN.md Decisions table)
- **Async driver: asyncpg via `postgresql+asyncpg`.** *Why:* mature and fast, and supported by `pgvector`. *When it fails:* asyncpg raises on more than 32,767 bind parameters (avoided with array parameters and chunked upserts) and on aware datetimes in naive columns (avoided by `_naive()` in `Database`).
- **Alembic layout: `alembic.ini` at the root, scripts packaged in `orbit/storage/migrations/`, one MetaData, numbered revisions.** *Why:* migrations ship in the image, and `alembic check` compares one source of truth. *When it fails:* an out-of-band schema edit shows up as `alembic check` drift in CI; a broken migration stops Orbit at startup with the Alembic error.
- **Embeddings: OpenAI `text-embedding-3-small`, 1536 dims.** *Why:* cheap and strong for English job text, and under pgvector's 2,000-dim index limit. *When it fails:* changing the model or dimension needs a migration plus a re-embed (`embedded_hash = NULL`); the router raises on a wrong vector count, and the embed stage rejects wrong dimensions.
- **Extraction: `gpt-5-mini` on the `extract` task, with a strict JSON-schema response format.** *Why:* this is a small-model job, and strict mode removes shape errors. *When it fails:* semantic errors are caught by validators plus one retry, then recorded as `failed`. Swap the model in `config.yaml` and compare with `orbit radar eval`. *Update 2026-10-15:* `extract` now uses `gpt-6-luna` (OpenAI list price $0.10 input / $0.50 output per 1M tokens, against $0.25 / $2.00 for gpt-5-mini; also supports structured outputs and `reasoning_effort: low`). Its extraction accuracy has not been measured yet: run `orbit radar eval` once a key is set and switch back if it is worse.
- **Embeddings go through the router (`Provider.embed`, `ModelRouter.embed`).** *Why:* code names a task and config picks the model, and the fakes cover it in tests. *When it fails:* a missing key skips the stage with one warning instead of crashing.
- **Raw payload: the latest API response per posting in `raw` (JSONB), plus `content_hash`.** *Why:* allows debugging and re-normalizing without re-fetching, and only real content changes trigger re-extraction. *When it fails:* there is no history of earlier versions (out of MVP scope); a hash-definition change re-extracts everything once.
- **Resume input: a `.md`/`.txt` file at `radar.resume_path`.** *Why:* clean text, with no PDF parser. *When it fails:* other formats are rejected with a clear message; export the resume to text once.
- **Notifications: one message per match, at most 5 per poll plus a digest, UNIQUE `posting_id`.** *Why:* easy to act on from a phone, no first-run flood, and "never twice" is enforced by the database. *When it fails:* see "Notification delivery (M6.1)".
- **Test DB: real Postgres + pgvector, migrated once, truncated per test; tests fail instead of skipping without a DB.** *Why:* SQLite can't test pgvector, JSONB or ON CONFLICT. *When it fails:* tests can't run without Postgres (start it with `docker compose up -d postgres`). The name guard stops tests from wiping a real DB.
- **Lint: `ruff check` with E, F, W, I, B, UP at line length 120; `ruff format` not enforced.** *Why:* catches real bugs with minimal churn. *When it fails:* formatting drifts between files (about 12 files would be reformatted); enforcing it later is one mechanical commit.
- **ORM tables in `orbit/storage/models.py`, Pydantic domain models in `orbit/radar/models.py`.** *Why:* one Alembic metadata, and the radar layout CLAUDE.md asks for. *When it fails:* a radar table defined anywhere else would be invisible to `alembic check`.
- **Watcher hooks `bind`, `close` and `on_pushed`, all no-ops by default.** *Why:* the radar needs the router, cleanup and delivery results without changing the watcher interface. *When it fails:* an exception in a hook is logged and contained (a watcher that fails to bind is skipped, a failing `on_pushed` leaves rows pending, which then expire and are never re-sent).
- **Radar CLI talks to the DB directly, not through the daemon.** *Why:* batch commands work while the daemon is down and don't hold HTTP requests open for minutes. *When it fails:* a manual run alongside the watcher isn't locked against it (rare and harmless, because writes are idempotent and claims are atomic).
- **Timestamps: naive local `timestamp`, ISO strings at the `Database` boundary.** *Why:* the existing reminder code and CLI parse these strings, so M1 needed no caller changes. *When it fails:* a host timezone change shifts the meaning of stored times. Containers pin `TZ` (default America/Toronto).

## Local Postgres: Docker Compose first, pgserver fallback (M1.1)
- **Chose:** `docker compose up -d postgres` (`pgvector/pgvector:pg16`, bound to 127.0.0.1:5432). An init SQL script creates the `orbit_test` database and the `vector` extension in both DBs. `scripts/dev_postgres.py` (pgserver) remains for machines without Docker.
- **Why:** Docker became available on the dev machine after planning. Compose gives the same image as CI and production, and pgserver stays as a zero-admin fallback.
- **When it fails:** if the Docker daemon is down, Orbit can't connect at startup and `/health` reports `db: error`. Start Docker Desktop, or run `python scripts/dev_postgres.py` and point `DATABASE_URL` at the URI it prints.

## Core table column types (M1.3)
- **Chose:** `BIGINT` identity-style ids (`BIGSERIAL`), bounded `VARCHAR` for short identifiers (session 200, role 20, channel 50, chat_id 100, model 100, kv key 200), `TEXT` for message content and reminder text, kv values as `JSONB`, plus indexes on `messages(session, id)`, `reminders(status, due_at)` and `usage(created_at)`.
- **Why:** the indexes match the only query patterns (`get_history`, `list_reminders`/`reminders_between`, `usage_since`). Bounded identifiers catch garbage early, and JSONB lets later code query kv values.
- **When it fails:** a value longer than its bound raises a `DataError` on insert, which surfaces as an error in the agent or tool reply rather than as silent truncation. Widening a column is a one-line migration.

## Migrations run on startup as well as in the container entrypoint (M1.4)
- **Chose:** `OrbitApp.start()` calls `Database.migrate()`, which runs `alembic upgrade head` in-process through `orbit/storage/migrate.py` (a programmatic Alembic `Config` pointing at the packaged `migrations/`, no `alembic.ini` needed). The CLI `alembic` command still works for manual use.
- **Why:** the Windows Task Scheduler mode runs `orbit serve` directly with no entrypoint script, so without this a fresh install or an upgrade would start on a stale schema. `upgrade head` is idempotent and takes milliseconds when nothing is pending.
- **When it fails:** a broken migration stops Orbit at startup with the Alembic error in `logs/orbit.log`. That is intentional: running on a half-migrated schema is worse. Fix the migration, or `alembic downgrade -1` to roll back.

## Test database guard (M1.4)
- **Chose:** tests read `TEST_DATABASE_URL` from the environment or `.env`, fail (not skip) if it is missing, and refuse any URL whose database name does not contain `test`.
- **Why:** the fixture truncates every table before each test, and one mistyped URL would wipe real conversation history and reminders.
- **When it fails:** pytest stops immediately with a message that says what to set.

## Parallel tasks: one worktree and one test database each (CLAUDE.md parallelism rule)
- **Chose:** each parallel subagent works in its own git worktree, runs the main venv's Python with `python -m ...` from the worktree root (so the worktree's `orbit` package is imported before the editable install), and uses a private database `orbit_test_<task>` on the shared Postgres. Agents never edit PROGRESS/QUESTIONS/LEARNING/DECISIONS; the coordinator merges branches one at a time, runs the full suite after each merge, and writes the tracking docs.
- **Why:** the `db` fixture truncates every table, so two agents on one test DB would corrupt each other's runs. Keeping shared docs coordinator-only removes the main source of merge conflicts.
- **When it fails:** a worktree created from the wrong base (seen once: worktrees started from `main`) is caught by checking each branch's parent commit before merging. A merge conflict means the branch is rebased onto the new head and its tests are re-run before merging.

## CI details (M1.9)
- **Chose:** `DATABASE_URL` and `TEST_DATABASE_URL` both set at job level to the service DB `orbit_test`; an explicit `alembic upgrade head` step before pytest; a 15-minute job timeout; a 10×5s service health check.
- **Why:** the separate migration step gives a clear "migration failed" signal on a clean database before any test runs (the fixture's own upgrade is then a no-op). Without `DATABASE_URL`, Alembic would fall back to the `orbit` DB, which doesn't exist in CI, so it fails loudly instead of migrating the wrong place.
- **When it fails:** a red run blocks the merge. `docker compose config -q` passes today only because compose needs no `.env`. **M1.8 must keep that true** (`env_file` with `required: false`), or CI must create an empty `.env` first.

## Router embeddings details (M5.1)
- **Chose:** `ModelRouter.embed` uses the same `resolve()` as `complete` (an unknown task falls back to `chat`), never splits batches, and raises `RuntimeError` if the provider returns a different number of vectors than texts. `FakeProvider` records embed calls in a separate `embed_calls` list.
- **Why:** one resolution path keeps "code names a task, config picks the model". Callers (M5.3) store vectors by position, so a short response must never silently attach vectors to the wrong posting. Keeping chat and embed calls apart means existing tests that index `calls[0]` are unaffected.
- **When it fails:** a mistyped task name sends the embeddings request to the chat model and the API rejects it; the error surfaces to the caller. On a count mismatch the whole batch fails with no writes and no usage recorded, and the pipeline leaves those postings un-embedded (`embedded_hash != content_hash`) so the next poll retries them.

## /health semantics (M1.7)
- **Chose:** `OrbitApp.db_health()` pings with a 2 s `asyncio.wait_for` timeout and never raises; `/health` returns HTTP 503 with `status: "degraded"` and a short `"<ExceptionType>: <first line>"` error (≤200 chars) when the DB is down. `/status` gains `"db"` but still needs the DB for its other fields.
- **Why:** the Docker healthcheck and `curl -f` act on the status code, so `/health` must answer even when Postgres hangs, without leaking tracebacks.
- **When it fails:** a DB slower than 2 s reports as degraded (`TimeoutError`). On Windows a refused localhost connection takes about 2 s, so it can also show as a timeout. `/status` returns 500 while the DB is down, as it did before; use `/health` for liveness.

## SQLite → Postgres copy semantics (M1.6)
- **Chose:** rows whose id (or kv key) already exists in Postgres are skipped, not overwritten; all four tables and the sequence bumps are copied in one transaction, after reading the whole SQLite file; invalid JSON in kv aborts the run.
- **Why:** re-runs are safe and never clobber data Orbit wrote after the switch, and a partial copy is impossible.
- **When it fails:** if Postgres already holds unrelated rows with the same ids, those SQLite rows are skipped; the first run's "skipped" count shows it, so migrate into an empty DB. One bad row aborts the whole run with the error and writes nothing; fix the row and re-run.

## Radar schema details (M2.1)
- **No ANN index yet.** `<=>` queries on `radar_postings.embedding` run as exact scans. There will be a few thousand postings at most, an exact scan takes milliseconds, and exact search needs no tuning. *When it fails:* if scoring or search gets slow (around 100k rows), add an HNSW `vector_cosine_ops` index in a new migration; queries already use `<=>`, so no code changes.
- **No custom Alembic type comparison for `vector`.** pgvector 0.5.1 registers the type for reflection, and `alembic check` detected a deliberate `vector(3)` vs `vector(1536)` drift during testing. *When it fails:* if a pgvector release drops that registration, Alembic warns "did not recognize type 'vector'"; then add a narrow `compare_type` hook for VECTOR only.
- **Python-side timestamp defaults.** `created_at`, `first_seen_at`, `last_seen_at`, `started_at` and `updated_at` use `default=_now` (naive local, no microseconds) rather than `server_default=now()`, because Postgres in Docker runs in UTC while Orbit stores local time. The default also applies to Core `insert()` and `ON CONFLICT` statements. *When it fails:* raw SQL inserts must set these columns themselves, or NOT NULL raises.
- **Column choices.** Job-board text (title, url, location_raw, department, description_text) is `TEXT`, so long values never fail; adapters store `""` for missing location or description, since those columns are NOT NULL. Hashes are `VARCHAR(64)` (sha256 hex), and score is `DOUBLE PRECISION`. The composite unique constraint is named explicitly `uq_radar_postings_source_external_id`. *When it fails:* adding a fourth job board needs a migration that widens the `source` CHECK constraint.

## Profile embedding (M5.2)
- **Chose:** before hashing, the text is normalized (CRLF→LF, strip, files read as `utf-8-sig`). Re-embedding is skipped only when the hash matches *and* an embedding exists. No DB session is held open during the embed call. Text sent to the embedder is cut at 24k characters, while the full text is stored. Radar CLI commands record usage through `db.add_usage` like the daemon. The radar sub-app is mounted on `orbit` now (pulled forward from M2.5), with one `open_runtime` helper that later commands and tests reuse. Only `.md` and `.txt` resumes are accepted.
- **Why:** a resume saved on Windows and one saved on Unix must hash the same; a row missing its embedding repairs itself on the next run; embedding costs money, so it must show up in usage even outside the daemon; character truncation needs no tokenizer dependency.
- **When it fails:** non-UTF-8 files and a missing API key exit 1 with a one-line message. Text that tokenizes far denser than English could still exceed the model's token limit, and that API error currently surfaces as a traceback. If two processes write the same profile at once, the last write wins, which is harmless. Every `orbit` command now imports SQLAlchemy at startup, so the CLI starts slightly slower.

## Source adapters and polite HTTP (M2.2)
- **Chose:** each adapter exposes `board_request(board_token) -> (url, params)`, which the fixture recorder reuses. Requests take the global 4-slot semaphore, then wait for the per-host 1 s spacing; backoff sleeps happen outside the semaphore. 429/500/502/503/504 and transport errors retry with 1/2/4 s backoff (no jitter); other non-2xx responses (such as 404) raise immediately. A `Retry-After` over 60 s makes the client give up instead of retrying early. `content_hash` is sha256 over sorted-key JSON of the stripped title, location_raw, department and description_text; URL, ids, raw payload and timestamps are excluded. Fixtures keep the real response structure, put intern and co-op postings first, and are trimmed to ≤8 KB per job.
- **Why:** respecting the boards' limits matters more than speed at about 30 companies every 30 minutes. Hashing only the fields extraction reads means re-extraction happens only when the content that matters changes.
- **When it fails:** a company whose fetch keeps failing is recorded as a failed run (M3.2) and retried next interval, and its open postings are left untouched. Changing the hash's field set invalidates every stored hash, which triggers a one-time re-extraction of all postings. An adapter that needs paging would need a different recorder hook.

## Container details (M1.8)
- **Chose:** migrations ship as package data (`migrations/` has no `__init__.py`). The image keeps the `orbit/` source in `/app` next to the installed package, so `alembic.ini`'s script path works. Dependencies install in their own layer. The listen address is overridable through `ORBIT_API_HOST/ORBIT_API_PORT` in `Settings`, while the CLI still dials config.yaml's host. Compose `environment` pins `ORBIT_HOME=/app`, `DATABASE_URL` (service host `postgres`) and the port, because `environment` beats `env_file` and the host `.env` points at 127.0.0.1. The service also sets `TZ=${TZ:-America/Toronto}`. `STOPSIGNAL SIGINT` plus `exec orbit serve`. Non-root uid 1000. The healthcheck uses Python urllib (the slim image has no curl).
- **Why:** Orbit stores and schedules in naive local time, so a UTC container would fire the 08:00 briefing at 04:00 Toronto time. Orbit only shuts down cleanly on KeyboardInterrupt (SIGINT). uid 1000 matches the usual first Linux user (such as ec2-user), so bind mounts stay writable.
- **When it fails:** a new folder under `migrations/` needs its own package-data pattern, or startup stops with an Alembic "can't find scripts" error. On Linux, bind-mount folders auto-created by Docker are owned by root and Orbit can't write logs; the deploy script (M7.3) must `mkdir` and `chown 1000` `data/ logs/ memory/` first. A wrong `TZ` only shifts schedules.

## Posting sync semantics (M3.1)
- **Chose:** `sync_company` takes an `AsyncSession` and never commits. The extraction and score reset is decided inside the upsert SQL (`CASE WHEN content_hash = excluded.content_hash …`). The counts come from a `FOR UPDATE` pre-read and don't overlap (a closed posting that returns counts as reopened even if its content also changed). Only the hashed fields count as a change (a new URL or raw payload is stored without resetting extraction). A source mismatch raises `ValueError`. Fetched ids are passed as one array parameter, and the upsert is chunked at 500 rows. **An empty successful fetch closes all of the company's open postings.**
- **Why:** the caller (M3.2) keeps the posting writes and its `radar_runs` row in one transaction. Putting the reset in SQL keeps the stored data correct even if the pre-read count is stale. Array parameters avoid asyncpg's 32,767 bind-parameter limit on large boards.
- **When it fails:** a caller that forgets to commit silently loses the sync. If a board ever returns HTTP 200 with a wrongly empty list, its postings close, then reopen on the next good poll with their extraction kept, and they are never re-notified, because `radar_notifications` is untouched. Under a concurrent writer the counts can be off by one, but the data stays correct.

## Lever and Ashby mapping (M2.3, M2.4)
- **Chose:** a Lever board token written `eu:<site>` is fetched from the EU host. `location_raw` lists the distinct locations in board order, joined with "; ", plus " (Remote)" or " (Hybrid)" from the workplace flag ("Remote" alone when no location is given). Lever department is `categories.department`, falling back to `team`. Descriptions come from the plain-text fields, with HTML (not unescaped twice) as the fallback. `updated_at` is None: neither API exposes it, and change detection uses `content_hash` anyway. Ashby postings with `isListed: false` are dropped. The URL falls back to `applyUrl`.
- **Why:** EU support needs no schema change. Extraction (M4) needs every location and the remote signal in one string.
- **When it fails:** an EU company seeded without the `eu:` prefix 404s, and `verify-sources` shows it. Roles listed in many countries produce long location strings that M4.1's validators must normalize. Changing the location format later changes every Lever and Ashby `content_hash`, which re-extracts them all once. At some companies Lever's `department` is just the company name; the raw payload keeps `team`, so extraction can still use it.

## Poll runs (M3.2)
- **Chose:** each company's `radar_runs` row is committed with `ok = NULL` before its fetch. On success, the sync and the run update commit together; on failure, a separate session marks the run `ok = false` with `"{Type}: {first line}"` (≤500 chars). Companies are polled concurrently with `asyncio.gather(return_exceptions=True)`. A single `now` timestamp is used for every write in a poll. An explicit `companies=` list ignores the active flag.
- **Why:** a crashed or hung run stays visible as an unfinished row. No DB connection is held during network I/O. Results are deterministic in tests.
- **When it fails:** stats and uptime must count only `ok IS TRUE` runs, and stale NULL rows are harmless. If the DB itself is down, the failure write is only logged and the row stays NULL. With hundreds of slow companies, SQLAlchemy's 30 s pool timeout could fail runs; the fix would be a DB semaphore.

## Extraction normalization (M4.1)
- **Terms:** Jan–Apr is Winter, May–Aug is Summer ("Spring" is an alias), Sep–Dec is Fall ("Autumn" is an alias). A dash, "to" or "through" makes a range ("May–Dec 2027" → Summer and Fall 2027); a slash, comma, "and" or "or" makes a list. Ranges longer than 4 terms (16 months, the longest PEY), backwards ranges, and leftover words ("Summer 2027 at Google", "ASAP") are rejected. "N/A", "TBD", "unknown" and blank entries are dropped, so an empty list means not stated. *Why:* matches Waterloo co-op terms; anything that can't be normalized must be rejected. *When it fails:* a US "Spring 2027" meaning Jan–May lands one term late. Unusual phrasing raises a ValidationError, which M4.2's single retry (with the error fed back) handles.
- **Locations:** Canadian cities → "City, XX" (built-in table plus any city with a known province); US cities → "City, ST"; others pass through tidied; "Hybrid" and "On-site" words are stripped. In remote locations, any mention of Canada wins ("Remote (US or Canada)" → "Remote (Canada)"), and a city attached to Remote is dropped ("Toronto (Remote)" → "Remote (Canada)"). *When it fails:* an unknown place passes through and simply won't match the location filters. That fails safe (no notification on location), but the US option is lost from "US or Canada" remotes.
- **Role type:** unknown non-empty strings map to `other`; empty input is rejected. **Tech stack:** lowercased, aliases canonicalized ("tf" deliberately left ambiguous), capped at 25. The validators never adjust `remote_ok` or `canada_eligible` from the locations, so eval measures the LLM's own judgment. The Python model ignores extra keys, while the OpenAI schema forbids them.

## Watcher scheduling (M3.3)
- **Chose:** an optional `first_run_delay_seconds` watcher key (the radar uses 60 s), so a restart doesn't delay polling by 30 minutes. Watcher jobs set `max_instances=1, coalesce=True` explicitly. A watcher whose constructor or `bind()` raises is logged and skipped instead of crashing startup. Each watcher's `close()` runs inside its own try/except. Unknown watcher keys are logged and ignored. Default terms are Summer 2027 and Fall 2027 (most Winter 2027 roles are filled by October 2026).
- **Why:** a radar misconfiguration must never take down chat and reminders, and overlapping polls would double-fetch every board.
- **When it fails:** a crash loop polls about once a minute, which is still within PoliteClient's limits. A poll longer than 30 minutes makes the next one skip with an APScheduler warning. A broken watcher is visible only in the log and by its absence from `/status` jobs. A manual `orbit radar poll` running at the same moment as the watcher is not guarded. `RadarConfig.resume_path` takes effect once M3.4 wires it into the CLI (a test keeps it equal to `DEFAULT_RESUME_PATH` meanwhile). If your co-op sequence differs, edit `radar.terms` in config.yaml. *Update 2026-10-15:* config.yaml now sets `["Winter 2027", "Summer 2027"]` (the owner's co-op sequence); the code fallback in `RadarConfig` is unchanged.

## Seeds and verification (M2.5, M2.6)
- **Chose:** `seeds.yaml` owns name, source, board_token and hq_city; the database owns `active` (new rows start active, and re-seeding never re-activates a company unless the YAML says `active: true`). Companies removed from the file are never deleted (deleting would cascade away notification history and break "never twice"); they are listed, and `--prune` deactivates them. Changing a company's source or token clears its stale `last_verify_*`. Two slugs on the same (source, token) board are rejected. A board that returns 200 with no postings counts as OK. `--min-ok` defaults to 20, or to 1 with `--source`. Large US companies with real Canadian engineering offices (Stripe, Pinterest, Instacart, Faire, Tenstorrent) are included and marked as such.
- **Why:** hand-made choices in the DB survive re-seeding, and verification checks the board is reachable, not that it currently has openings.
- **When it fails:** a dropped company keeps being polled until you run `--prune`. The intern title count is plain keyword matching ("Student Success Manager" counts as an intern posting); it is a verify hint only, not used for matching. Seed and verify print the harmless "no OPENAI_API_KEY" warning because the shared runtime builds a router.

## EC2 deployment shape (M7.3)
- **Chose:** the compose and buildx plugins come from pinned, sha256-checked GitHub releases (AL2023 dnf has no compose plugin). The prod override stops publishing Postgres (`ports: !reset []`, needs compose ≥2.24.4, which the script ensures); backups, restores and psql go through `docker compose exec`. The deploy script refuses a missing or default `POSTGRES_PASSWORD`, CRLF `.env` files, a 127.0.0.1 `PROXY_URL` and edits to tracked files on the instance. It takes a backup before every deploy and supports `--ref` for rollback. Memory limits are 640m for Postgres and 768m for Orbit. Backups are written to a `.partial` file, checked with `pg_restore --list`, renamed, then pruned to 14. Cron runs at 03:15 UTC via `cronie`.
- **Why:** a bad configuration should stop the deploy with a clear message instead of starting a broken container, and nothing on the instance should listen publicly.
- **When it fails:** a checksum mismatch stops the script before anything is installed. An OOM kill restarts Orbit (raise `mem_limit`). `scripts/migrate_sqlite_to_pg.py` can't reach the EC2 DB directly, so the runbook converts locally and ships a pg_dump. Running two Orbits on one Telegram token causes 409 errors and duplicate notifications (the runbook warns about this).

## Extraction calls and storage (M4.2)
- **Chose:** prefilter-skipped postings store `{"is_internship": false, "skipped_reason": …}` with `extraction_model = "prefilter"` rather than a full `PostingExtraction`. The prefilter skips only when the title has a seniority word *and* no student-like word appears in the title or the first 600 description characters; new-grad roles are always sent to the LLM. Only JSON and validation errors are retried (once, with the error fed back). Provider or network errors fail the posting immediately, and a batch stops starting calls after 3 consecutive provider errors. If the `extract` task can't be resolved (no API key), `extract_pending` raises before touching any row. Results are written with `WHERE content_hash = :hash`, so a posting that changed mid-call stays pending. Three calls run at a time, newest postings first.
- **Why:** a wrong skip is never revisited unless the content changes, while a missed skip costs one cheap call. An outage or missing key must not turn a whole batch into failed rows.
- **When it fails:** anything that validates stored extractions (eval, stats, chat tools) must first check `extraction_status = 'ok'`. Postings that failed on a network error need `--retry-failed` (M4.3) to run again. A student role whose title looks senior and that never mentions students would be skipped; the word lists are module constants with tests, so they're easy to adjust.

## `orbit radar poll` semantics (M3.4)
- **Chose:** exit code 1 only when every polled company failed (0 on partial failure and when there is nothing to poll). `--company` accepts only active slugs and combines with `--source` as an intersection. An unknown `--source` is rejected before the DB opens. With no PATH, `orbit radar resume` uses `orbit_home / radar.resume_path`.
- **Why:** this matches the watcher, where one stale board never fails a poll. Polling an inactive company would leave its postings open forever, because nothing else would poll it to close them.
- **When it fails:** a partial outage shows only as ERROR lines and the failed count in the totals. To poll a deactivated board, re-activate it in seeds.yaml first. A missing default resume costs a DB connect before the "not found" error.

## Pipeline stages and retries (M4.3)
- **Chose:** `run_pipeline` runs poll → extract → embed, each stage in its own try/except; a missing provider skips the stage with one warning per run. Each run also retries at most 3 open postings whose extraction failed on a provider error at least 6 hours ago, one at a time, stopping at the first error. Postings whose model reply was invalid twice (error prefixed `after retry:`) are never retried automatically. `orbit radar extract --limit` defaults to `max_extract_per_poll`.
- **Why:** network failures heal over time, while the same prompt will likely fail validation again. The cap keeps the cost tiny.
- **When it fails:** a posting that always gets a provider error is retried about 4 times a day forever (one call each). Invalid-reply postings need `orbit radar extract --retry-failed`. A large backfill takes several runs.

## Which postings get embeddings (M5.3)
- **Chose:** only open postings whose extraction succeeded with `is_internship = true`, and whose `embedded_hash` differs from `content_hash`. The embedding text is the title, company, extracted terms/locations/role/stack, then the description cut near 6,000 chars. Batches of at most 64 run outside any transaction and are written with a content-hash guard. Three failed batches in a row stop the run.
- **Why:** waiting for extraction means the vector includes the extracted fields and isn't redone right after; non-internships are never scored or notified. (Cost is not the real reason: text-embedding-3-small is cheap. Scope is.)
- **When it fails:** chat search (M6.2) can't rank non-internship or not-yet-extracted postings by similarity, so it falls back to keyword or recency for those. Changing the text format doesn't change `content_hash`, so re-embedding everything needs `UPDATE radar_postings SET embedded_hash = NULL`.

## Eval harness (M4.4, M4.5)
- **Chose:** eval calls `extract_posting` directly, without the prefilter, so it measures the model. An outage (3 provider errors in a row) aborts with no saved score, while an invalid reply counts as wrong on every field. Label files are validated strictly (unknown or missing keys, duplicate ids, snapshots over 6,000 chars), and labels must already be in canonical form. Snapshots are capped at 6,000 chars against production's 12,000. The CLI replaces characters the console can't print. For `remote_ok`, if the text says this position is hybrid, it is false even when the board tag says Remote.
- **Why:** an outage must not be stored as 0% accuracy, a typo must not silently drop a field, and the reviewer must see exactly the value being scored.
- **When it fails:** `is_internship` accuracy says nothing about the prefilter. A few long postings lose late sections in the snapshot, so scores measure slightly shorter inputs than production. Adding a new key to the label format needs a code change.

## Matching rules and scoring (M5.4, M5.5)
- **Chose:** unstated terms pass the term filter (`TERMS_NOT_STATED_PASSES = True`). Unstated locations fail unless `remote_ok` and `canada_eligible` are both true (`LOCATIONS_NOT_STATED_PASSES = False`). Config terms and locations go through the same normalizers as extraction; an empty list switches that filter off. Every run rescores all eligible postings with a current embedding in one UPDATE, and clears the score of open postings that no longer qualify. Closed postings keep their last score as history. Scoring needs no API key. `orbit radar top` rescores before printing, has `--new` to hide already-notified postings, and draws a line at the notify threshold.
- **Why:** many internship postings never name the term, but an unknown location is no evidence of a Canadian office. Rescoring everything needs no bookkeeping, and a new resume or goal takes effect on the next run.
- **When it fails:** a posting for an unwanted term that never names it can still notify (flip the constant), and a Toronto posting the model extracted with no location is missed. Every scored row is rewritten every 30 minutes, which is harmless at a few thousand rows. A command that looks read-only (`top`) writes scores, idempotently and exactly as the watcher would.

## Notification delivery (M6.1)
- **Chose:** a new match is claimed with one atomic `INSERT … SELECT … ON CONFLICT (posting_id) DO NOTHING RETURNING`. A posting that has a notification row is never claimed again, whatever happens later to its score or status. Failed rows are retried (moved back to pending atomically) only while the posting is still open and above the threshold, for at most 3 pushes; retries are sorted in with new matches by score, with no backoff. At each claim, `pending` rows older than 1 hour are marked failed with "delivery unknown (process stopped before confirmation)" and attempts=3, so they are never re-sent (**at-most-once**). Overflow beyond `max_notifications_per_poll` is claimed and rides on the digest's push result. A cap of 0 disables notifications. Only the watcher passes `notify=True` to the pipeline. Messages are plain text, at most 3900 characters.
- **Why:** CLAUDE.md says never notify twice, so a crash may lose one notification (it still shows in `orbit radar top`) but must never duplicate one. Claiming overflow prevents a first-run flood of 5 messages plus a digest on every poll.
- **When it fails:** a push that reported failure but actually reached Telegram (a timeout after acceptance) is sent again on retry, which is the only path to a duplicate. Postings that only appear as a count in a digest are hidden by `top --new`. Turning notifications back on after a cap of 0 sends every eligible open match, capped and digested. The stored error is generic ("no channel delivered the message"), because `push()` returns only a bool; the channel error is in the log.

## Chat search tools (M6.2)
- **Chose:** `internship_only` (default true) limits search to postings whose extraction succeeded and say internship. Term, location and role filters require an ok extraction, so unextracted postings are reachable only by keyword with `internship_only=false`. The term rule matches scoring (postings that name no term pass). Location search is literal: a city matches any extracted location containing it, a province matches `, XX`, "Canada" adds remote-and-Canada-eligible roles, and "Remote" matches remote roles; a city search does not add remote roles. Ranking: with a usable `embed` task, embedded postings rank by cosine similarity, then keyword matches fill the rest; otherwise everything is ranked by a whole-word regex with weights title 3 / company 2 / description 1; an empty query ranks by score, then recency. Invalid filters return `error: …` with the allowed values. `notified` means a *sent* notification. The registry docstring parser now treats deeper-indented `Args:` lines as a continuation of the previous parameter.
- **Why:** "AI" must not match "maintain", the model needs the filter keys spelled out in the schema, and an error string lets the LLM correct itself and retry.
- **When it fails:** semantic mode has no similarity floor, so weak queries still return the nearest embedded postings ahead of keyword-only ones. Non-Canadian countries match only as substrings ("United States" misses "Seattle, WA"). A badly indented tool docstring yields a truncated parameter description.

## Stats definitions (M6.3)
- **Chose:** "verified" means active with `last_verify_status = 'ok'`. Extraction counts cover all stored postings, open and closed. "Scored" counts open postings with a score, the same set `top` ranks. Stats never rescores; it only reads. Latency is `percentile_cont(0.5 / 0.9)` of `sent_at - first_seen_at` over sent rows only. Uptime is distinct local calendar days with at least one `ok IS TRUE` run, and the 24 h window counts true and false runs (NULL in neither). Model usage today is shown for extract and embed. `radar:last_eval` is read defensively (a missing flag means unverified, malformed fields are skipped). `--json` output is ASCII-escaped.
- **Why:** each number matches how the earlier milestones define its state, and a hand-edited kv value must never crash stats or hide the unverified warning.
- **When it fails:** "verified" goes stale until `verify-sources` runs again. "Scored" can lag by one poll. Latency includes time a posting waited below the threshold (for example, before a resume change), so it is end-to-end, not pipeline speed. Moving the host to another timezone shifts the day boundaries for uptime.

## Role filter and threshold calibration (2026-10-16, after the first real run)
- **Chose:** a hard `radar.role_types` filter (`[swe, ml_ai, infra, data, research]` in config.yaml) inside `eligible_postings_filter`, validated strictly against `RoleType` at config load; an empty list means any role. A radar goal ("Software engineering, AI/ML engineering or AI agent co-op, Winter 2027, Python/TypeScript backend or LLM systems") blended in at 20%. `notify_threshold: 0.50`, just below Stripe's Software Engineer intern (0.503), the lowest technical role wanted.
- **Why:** the first real `top 30` (gpt-6-luna extraction, text-embedding-3-small) put three finance internships (0.531–0.537) above Stripe's SWE intern (0.513), so no threshold could separate wanted from unwanted roles. Embedding similarity measures "internship in Canada for Winter 2027" about as strongly as the kind of role, so role is a rule, not a score. With the filter and goal, technical internships scored 0.485–0.571 and 11 of the 12 eligible postings clear 0.50.
- **When it fails:** a misextracted `role_type` defeats the filter. Wealthsimple's "Client Experience Strategy & Operations" intern was extracted as `data` and scores 0.569. PhD-only research roles (Waabi, Stripe) and analyst roles also pass on role type. A typo in `role_types` stops Orbit at startup with the allowed values listed. Re-calibrate after changing the resume or goal (scores shift).

## Drop `data` roles and skip PhD titles (2026-10-16)
- **Chose:** `role_types: [swe, ml_ai, infra, research]` (no `data`). The prefilter now skips any title that names a PhD (`PhD`, `Ph.D.`, `Ph D`, `PhDs`, whole word, any case) before the student-word veto, so "PhD ... Intern" is skipped with no LLM call. Rows already extracted on the dev DB were re-checked once with the new rule (6 PhD postings re-marked `skipped`).
- **Why:** after the first calibration, four unwanted postings scored above wanted SWE roles. Three passed as `data` (Wealthsimple ops misextracted as `data`, 1Password and Stripe analytics) and one was a PhD-only research role (Waabi). No threshold could remove them. The goal targets SWE, ML/AI and agent roles, not analytics, and an undergrad is not eligible for PhD-only internships. After the change, `top 30` lists 7 technical internships at 0.503–0.571, all above `notify_threshold` 0.50.
- **When it fails:** an ML-engineering role extracted as `data` is now dropped too. The PhD rule reads the title only: a PhD-only role whose title does not say so (Cohere's Research Internship asks for a PhD in its description) still passes, and a title like "Interns welcome, PhD not required" is wrongly skipped. Prefilter changes only reach postings extracted afterwards, so existing rows need a one-off re-check.

## Skip postings whose description requires a PhD (2026-10-16)
- **Chose:** `phd_requirement()` in the prefilter reads the description line by line for phrases that make a PhD the requirement: "pursuing / enrolled in / working towards / completing a PhD", "PhD students only", "only open to PhD candidates", "must be a PhD student", "PhD required". The PhD must follow the verb directly and must not be followed by another degree ("a PhD or Master's", "PhD/MS"), so "pursuing a Bachelor's, Master's or PhD" is kept. A match is ignored when its line names a preference ("preferred", "ideally", "a plus", "asset", ...) or sits under a short heading that does ("Preferred qualifications:"), until the next requirements-style heading. Like the title rule, it runs before the student-word veto.
- **Why:** Cohere's "Research Internship (Winter 2027)" says "you must be currently pursuing a PhD" only in its description and was pushed to Telegram. A dry run over the 47 open internships on the dev DB skipped exactly 2 (Cohere Research, Pinterest UX Quantitative Research) and kept all 7 that accept a Master's or Bachelor's too (Pinterest ML interns, Faire, Waabi Research, two Stripe roles).
- **When it fails:** it is a phrase list, so new wordings ("doctoral candidates", "PhD-level students") slip through, and an exception clause is not read ("we will also consider exceptional non-PhD candidates" still skips Cohere's posting). A short unrelated line containing "plus" or "asset" can open a "preferred" section early and hide a real requirement (the posting is then kept, the safe direction). Already-extracted postings need the one-off re-check.

## Anthropic as a second provider (2026-10-16)
- **Chose:** `AnthropicProvider` on the official `anthropic` SDK behind the existing `Provider` protocol, selected per provider with `type: anthropic` in config.yaml and keyed by `ANTHROPIC_API_KEY`. It translates Orbit's OpenAI-format messages and tools to the Messages API, never sends `tool_choice`, turns the radar's `response_format` into structured outputs (`output_config.format`), maps `effort` to `output_config.effort`, and `cache_system: true` caches the system prompt. Tool-calling turns keep their raw blocks (`provider_blocks`) so thinking blocks go back verbatim. Routing at first: chat, briefing, code on claude-sonnet-5-5; extract (effort low, cached system prompt), fast, summarize on claude-haiku-5-5; embed stays on OpenAI text-embedding-3-small (1536 dims, no migration). Changed the same day, see the next entry.
- **Why:** a second vendor behind the router shows the abstraction holds, and lets each task use the better model. Keeping embeddings on OpenAI avoids a schema migration and a full re-embed (Anthropic has no embeddings API).
- **Eval (30 unverified labels, both at low effort):** gpt-6-luna vs claude-haiku-5-5: is_internship 100 / 100%, terms 93.3 / 90.0%, locations 86.7 / 80.0%, remote_ok 93.3 / 96.7%, canada_eligible 100 / 96.7%, role_type 93.3 / 86.7%, tech_stack 86.7 / 80.0%, 0 failures each. Both cost $0.10 / $0.50 per MTok in/out with $0.01 cache reads. Haiku used ~3,860 input tokens per posting (about 1,950 of them a cached prefix) and 138 output: $0.0285 per 100 extracted postings, 17.5 s for 30. Luna used ~2,230 input and 201 output: about $0.032 per 100 at list price with no cache hits (the measured run was almost fully cached by an immediately preceding run, so its $0.012 is not representative), 31 s for 30. Cost is a wash; Luna was more accurate on 5 of 7 fields.
- **When it fails:** without `ANTHROPIC_API_KEY` the anthropic provider is skipped and every Claude-routed task fails to resolve, so chat, briefing and extraction stop until the key is added or the tasks are routed back to openai. Message translation covers text, tool calls and tool results only (no images). The no-tools final round flattens tool history to text. Structured outputs reject some JSON Schema keywords; `transform_schema` moves them into descriptions, so they are no longer enforced by the API (Pydantic validation still runs).
