# Internship Radar MVP: plan

Branch: `radar-mvp`. Rules for agents live in `CLAUDE.md`. Progress is tracked in `PROGRESS.md`, open questions in `QUESTIONS.md`.

## MVP acceptance criteria

- `docker compose up` starts orbit and postgres (pgvector). Orbit's existing features (chat, reminders, briefing, CLI) work on Postgres, all pre-existing tests pass, and GET /health on the local API reports DB status.
- At least 20 Canadian tech companies seeded across Greenhouse, Lever and Ashby source adapters, each checked by `orbit radar verify-sources`.
- The internship_radar watcher polls every 30 minutes, dedupes on (source, external_id), and marks postings closed when they disappear; covered by tests using recorded API fixtures.
- LLM extraction through the router into a validated Pydantic model (is_internship, terms, locations, remote_ok, canada_eligible, role_type, tech_stack); failures recorded with the error; tests use a fake client.
- Eval: `orbit radar eval` reports per-field accuracy against a labeled set, plus 30 draft labels in a file marked "UNVERIFIED — needs human review".
- Matching: resume text from a local file is embedded; postings are scored with pgvector similarity plus rule filters (term, location, internship only); `orbit radar top 10` prints the best matches with scores.
- Notifications: new postings above a score threshold reach me on Telegram through Orbit's existing push path, once and never twice.
- Chat tools: search_postings(query, filters) and set_radar_goal(text) as @tool functions, so I can ask Orbit "any new AI co-ops in Toronto?".
- CI: GitHub Actions runs ruff and pytest (with Postgres) on every push and is green.
- Docs: README updated with a Mermaid architecture diagram, setup steps and metrics; docs/DECISIONS.md; LEARNING.md; deploy/ with an EC2 deploy script and runbook (prepared, not executed).

Out of scope: running the AWS deploy, a web frontend, an MCP server, Discord, 👍/👎 feedback, multiple users.

## Current architecture

Snapshot of `main` at 7067f98 (about 2,000 lines of Python, 7 tests).

**Wiring.** `orbit serve` calls `orbit.app.main()`, which builds one `OrbitApp`. Its constructor creates everything once: `Settings` (secrets from `.env`), `Config` (`config.yaml`), the SQLite `Database` (`data/orbit.db`), the markdown `MemoryStore` (`memory/MEMORY.md`), the `ModelRouter`, the `Agent` and the `OrbitScheduler`. `start()` connects the DB, starts each channel with `OrbitApp.handle` as its message callback, starts the scheduler, and optionally pushes "Orbit 已上线" to Telegram.

**Channels.** A `Channel` is a protocol with `start(handler)`, `stop()`, `send(chat_id, text) -> bool` and `default_chat_id()`. `TelegramChannel` long-polls and only answers the owner chat id. `LocalApiChannel` runs FastAPI/uvicorn on `127.0.0.1:8765` inside the same event loop; the `orbit` CLI (`orbit/cli/main.py`, Typer) is a thin HTTP client for it (`/chat`, `/status`, `/push`, `/reminders`, `/jobs`, `/briefing`, `/history/clear`). The CLI channel cannot receive pushes (`default_chat_id()` is `None`).

**Message flow.** Channel → `OrbitApp.handle(Incoming)` → `Agent.handle(channel, chat_id, text)`. The agent keys the conversation as `"{channel}:{chat_id}"`, loads the last `history_turns` messages from the DB, stores the user message, and builds `[system, *history, user]`. The system prompt is `persona/system.md` + the current time + the full `MEMORY.md`. It then loops up to `max_tool_rounds`: `router.complete("chat", messages, tools=registry.schemas())`; if the response has tool calls, it appends the assistant message and one `role: tool` message per call (`registry.call(name, args, ToolContext)`) and loops; otherwise the text is the reply. If the limit is hit it makes one last call without tools to force an answer. Exceptions become a Chinese error string, never a crash. The reply is stored and returned to the channel. `Agent.generate(task, prompt, skill)` is the one-shot path used by jobs (system prompt + optional `persona/skills/<skill>.md`).

**Router and providers.** Code only names a *task*. `ModelRouter.resolve(task)` looks it up in `config.tasks` (unknown tasks fall back to `chat`), picks the provider by name, and merges the task's `params` with per-call overrides. Providers are built from `config.providers` and skipped when their API-key env var is missing. There is one implementation, `OpenAIProvider`, which wraps `AsyncOpenAI.chat.completions.create` for any OpenAI-compatible endpoint (optional proxy), and returns a uniform `Response(text, tool_calls, usage, raw)`. After each call the router reports token usage to a `usage_sink`, which `OrbitApp` writes to the `usage` table. There is no embeddings API yet.

**Tools.** `orbit/core/tools/registry.py` holds one global `ToolRegistry`. `@tool` registers a plain sync or async function: the JSON schema comes from type hints (`str/int/float/bool/list/dict`, Optional unwrapped) and the docstring (first paragraph = description, `Args:` lines = parameter descriptions). A parameter named `ctx` is not exposed; it receives a `ToolContext(channel, chat_id, db, memory, scheduler, extra)`. `registry.call` never raises: errors become `"error: ..."` strings and non-string results are JSON-encoded. Built-in tools (`current_time`, `remember`, `forget`, `set_reminder`, `list_reminders`, `cancel_reminder`) register by being imported in `orbit/core/tools/__init__.py`.

**Scheduler.** `OrbitScheduler` wraps an `AsyncIOScheduler` in the local timezone. On start it re-schedules every pending reminder from the DB (`DateTrigger`, `misfire_grace_time=None`, so reminders missed while offline still fire), adds the briefing cron job (`jobs.briefing.cron`, default 08:00), and registers each `watchers:` entry from `config.yaml`. A reminder fires by re-reading the row, pushing `⏰ 提醒：…` via `OrbitApp.push` to its origin channel (falling back to any channel with a default chat, i.e. Telegram), and marking it `done` or `undelivered`. The briefing job builds a prompt from today's reminders + memory, calls `agent.generate("briefing", …, skill="briefing")` and pushes it. Watchers: `@register_watcher("type")` puts a `Watcher` subclass in `WATCHER_TYPES`; the scheduler instantiates it with the remaining config keys as kwargs and adds an `IntervalTrigger(minutes=interval_minutes)` job that calls `await watcher.check(db)` and pushes each returned `Event` as `"[name] title\nbody"`. No concrete watcher exists yet, and push results are not reported back to the watcher.

**Storage.** `orbit/storage/db.py` is a hand-written `aiosqlite` wrapper. `connect()` runs a `CREATE TABLE IF NOT EXISTS` script (no migrations) for four tables: `messages(session, role, content, created_at)`, `reminders(channel, chat_id, due_at, text, status, created_at)`, `usage(task, provider, model, prompt_tokens, completion_tokens, created_at)` and `kv(key, value-as-JSON)`. Timestamps are naive local ISO strings, and callers depend on that (`due_at.replace('T',' ')`, `datetime.fromisoformat(r["due_at"])`, `r['due_at'][11:16]`). Rows come back as plain dicts. Every write commits immediately. Long-term memory is not in the DB: it is the markdown file `memory/MEMORY.md`, edited by the `remember`/`forget` tools.

**Tests.** `tests/conftest.py` provides a scripted `FakeProvider`, a `make_config()` with `chat` and `fast` tasks, a SQLite `db` fixture in `tmp_path`, and a `memory` fixture. The 7 tests cover the agent tool loop and history, the reminder tool, the round-limit guard, registry schema generation and error handling, and router task resolution and usage reporting.

## Decisions

| Topic | Choice | Reason |
|---|---|---|
| Async Postgres driver | `asyncpg` via SQLAlchemy's `postgresql+asyncpg` dialect | It is the most mature and fastest async driver, the `pgvector` Python package supports it, and it is what the SQLAlchemy async docs use. |
| Alembic layout | `alembic.ini` at the repo root, scripts in `orbit/storage/migrations/` (async `env.py`), all ORM tables (core and radar) in `orbit/storage/models.py` as one `MetaData`; numbered revision ids (`0001_core`, `0002_radar`) | Migrations ship inside the package for the Docker image, one metadata keeps `alembic check` autogenerate diffs honest, and numbered ids keep history readable. The container runs `alembic upgrade head` before `orbit serve`. |
| Embedding model and dimension | OpenAI `text-embedding-3-small`, 1536 dims, `vector(1536)` | It is cheap and strong for English job text, and it stays under pgvector's 2000-dim index limit. Changing the model means a new migration and a re-embed, which is documented. |
| Extraction model | `gpt-5-mini` on a new `extract` task, with `response_format` JSON schema generated from the Pydantic model | Structured fields are a small-model job, schema-constrained output cuts validation failures, and it is the existing `fast`/`summarize` model, so there is no new provider. |
| How the router exposes embeddings | `Provider.embed(model, texts)` + `ModelRouter.embed(task, texts)`, resolved through `config.tasks` like `complete`, reporting usage to the same sink | It keeps "code names a task, config picks the model", reuses the provider/API-key plumbing, and lets `FakeProvider` cover it in tests. |
| Raw payload storage | The latest raw API payload per posting in `radar_postings.raw` (JSONB), plus a `content_hash` of the normalized fields | It keeps debugging and re-normalizing possible without re-fetching, and the hash drives re-extraction only when content changes. There is no history table, since snapshot history is out of MVP scope. |
| Resume input format | A plain-text or Markdown file (default `data/resume.md`, git-ignored), path set by `radar.resume_path` | Embedding wants clean text. PDF parsing adds a dependency and noise; exporting a resume to text once is trivial. |
| Notification style | One Telegram message per matching posting (score, company, title, terms, location, link), at most `max_notifications_per_poll` (default 5) per poll, with the overflow in one digest message | Individual messages are easy to act on from a phone, and the cap stops a first-run flood. A `radar_notifications` row with a UNIQUE `posting_id` guarantees "never twice"; failed pushes retry up to 3 times. |
| Test database strategy | Real Postgres+pgvector at `TEST_DATABASE_URL`: `alembic upgrade head` once per session, `TRUNCATE … RESTART IDENTITY CASCADE` before each test; CI uses a `pgvector/pgvector:pg16` service container; tests fail (not skip) without a DB | SQLite cannot test pgvector, JSONB or `ON CONFLICT` semantics. Truncation works with `Database` methods that commit internally, which savepoint rollback would not. Failing loudly stops CI from going green on skipped tests. |
| Lint config | `ruff check` only: `target-version = "py312"`, `line-length = 120`, rules `E, F, W, I, B, UP`; `ruff format` not enforced | It catches real bugs and import order with minimal churn to the existing hand-formatted code, which has some lines over 100 characters. |
| Local Postgres on this machine | Docker Compose where available; this Windows box has no Docker or WSL, so dev uses the `pgserver` pip package (dev-only); if that fails, DB tests run in CI only and this is logged in QUESTIONS.md | It unblocks the autonomous build without requiring an admin install or reboot. |
| ORM tables vs domain models | ORM tables in `orbit/storage/models.py`; Pydantic domain models (`NormalizedPosting`, `PostingExtraction`) in `orbit/radar/models.py` | It keeps one Alembic metadata, and `orbit/radar/models.py` matches the layout in CLAUDE.md. |
| Watcher integration | Two optional hooks on `Watcher`: `bind(orbit)` (access to router and settings) and `on_pushed(event, ok)` (delivery result); both default to no-ops | The radar needs the router and delivery feedback for "never twice"; the hooks keep the existing interface and push path intact. |
| Radar CLI transport | `orbit radar …` commands open their own DB engine and router from `.env`/`config.yaml` instead of going through the daemon's HTTP API | Batch commands (verify, eval, top, stats) should work when the daemon is down and shouldn't hold an HTTP request open for minutes. |
| Timestamps | `timestamp without time zone` in local time, serialized to ISO strings at the `Database` boundary | It preserves the current behavior that the reminder code and CLI parse, so M1 needs no caller changes. |

## Risks

- **No local Docker/Postgres** on the dev machine (checked: no Docker, no WSL distro, no `psql`). Mitigated by M1.1's `pgserver` fallback and CI.
- **Seed churn**: companies switch job boards. `verify-sources` exists to catch this; seed 30 or more candidates to keep 20 or more passing.
- **Extraction cost on first poll**: hundreds of postings. Mitigated by the keyword prefilter and `max_extract_per_poll`.
- **Similarity threshold calibration**: `text-embedding-3-small` cosine scores cluster in a narrow band. Calibrate `notify_threshold` from the `top` output in M5.5 and record the value in DECISIONS.
